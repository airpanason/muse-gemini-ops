# 生成物の検証

生成した側の自己申告は、合否の根拠にしない。検証は、生成とは独立した材料と手順で行う。

## 1. 始める前に決めること

- 何をもって正しいとするか（合否を決める材料と基準）を、生成の前に定義する
- 失敗の形（どんな壊れ方をし得るか）を先に挙げる
- 合格の定義には、保証する範囲と保証しない範囲の両方を書く。範囲を書けないものは合格にしない

## 2. テストの分離

- 直しのループに使うテストと、最終判定に使うテストは分ける。判定用の材料は、生成する側に見せない
- 材料の分離が崩れた（判定用の答えが生成側から見える場所に置かれた）場合、その回の判定は無効として記録し、材料を作り直す
- 凍結した材料は変更しない。変える必要が出たら、版を上げて理由を記録する
- 仕様や要件に変更が入った場合は、該当する要件ID・設計項目に紐づくテスト材料をすべて特定し、再検証の対象から漏れないよう照合する

## 3. 検証の実施

- 本番と同じ流れを、正式な手順で発火して確かめる。手作業で似せて作った成果物はテストにならない
- 反証を最低1回試みる。壊しに行く材料で壊れなかったことを、合格の根拠の1つにする
- 落ちた項目は、件数と内容を隠さず報告する

## 4. 報告

- 合格と報告する時は、保証する範囲と保証しない範囲を分けて書く
- 検証できなかった部分は、未確認として明示する。黙って範囲から外さない

## 5. 文書推敲の機械検査

- 公開記事・仕様書・重要文書を推敲した時は、機械的な文章検査（表記・用語・意味保持のチェック）を併用する
- 検査を必須とする対象は公開・提出・正本系のみとする。チャット応答と内部ログ（作業ログ・引き継ぎ記録など、記録そのものが目的の文書）は対象に含めない
- 文書種別の対応は次のとおりとする。記事・ブログ原稿は article、仕様書・運用メモの正本は manual、PR・変更管理（CHG）文書は pr、インシデント記録は incident
- 検査の実行記録を、検証証跡として確認記録に残す
- 提出の直前に最終稿のハッシュを記録と照合する。検査の後に本文を書き換えたら、未検査のまま提出せず、検査を再実行する
- 「意味を変えずに直した」という自己申告だけで推敲の確認完了としない。検査の記録は「検査を実行した」ことを示すものであり、意味が保たれたことの合格判定ではない
