# 02. ワークフロー — 日常の運用サイクル・引き継ぎ手順

## 2.1 作業前の確認（常駐ルール）

Primary は作業を始める前に、必ず次の2点を確認する。

- 共有フォルダ `<shared-drive>/shared-canonical` の `PENDING-UPDATES.md`（更新待ち一覧）
- 運用メモの版

未取り込みの更新があれば、作業の前に取り込む。取り込んだら、作業ログに取り込んだ版と日時を記録する。

## 2.2 日常の運用サイクル

内容は次のとおり。

1. 本人が Primary へ単発作業を依頼する（データの無いものに限る）
2. Primary は作業前の確認（§2.1）を行い、スキルを取り込んで作業する
3. Primary は成果物を `<shared-drive>/primary-to-secondary` へ置き、ログ断片（`log-frag_`）もあわせて置く
4. Secondary は定期的に受け渡しフォルダを確認し、入口の機械検査（命名・形式・混入スキャン・改訂案の必須要素）を通したものだけを取り込む
5. Secondary は検証のうえで既存のフローへ流す（公開物はデプロイ手順で反映、改訂案は本人の承認へ回す）
6. 処理済みのファイルは、Secondary が名前の先頭に `done-` を付ける

## 2.3 記事・日報の下書きフロー（4点セット）— ケーススタディへ分離

記事や日報の下書き作成を Primary へ移管する場合のフローは、汎用の運用サイクル（§2.2）とは切り離し、`docs/examples/article-draft-flow.md` のケーススタディとして分離した。詳細はそちらを参照すること。

## 2.4 通知・報告の原則（NTF）

| ID | 原則 |
|---|---|
| NTF-01 | 状態系の通知は統合と圧縮を原則とする。チャットには件数、保存先、最小限の判断事項だけを送る。全文はファイルに置く |
| NTF-02 | 本文そのものが成果物である通知は、本文を届ける |
| NTF-03 | 即時通知は次の4場合に限る。期限直前、失敗、例外、本人が待っている作業結果 |
| NTF-04 | Primary が作成した記事下書きを Secondary が記事化フローへ上げる前に、Secondary は Primary へ最終版かどうかを確認し、返事を待ち合わせてから上げる。Primary は確認を受けたら、最終版であること、または未反映の修正があることを `memo_` ファイルで返す |
| NTF-05 | 日報は、確定後に Primary へ連携し、最終確認とタグ付けを受け、返事を待ち合わせてから投稿する。確定時の連携は1回にまとめる |

## 2.5 例外として認める自動実行（v1.0 では対象外）

定常実行（定期スケジュールでの自動実行）は原則として Primary の担当外であり、v1.0 には自動実行の例外を含めない。試行中の自動実行の例外（メール通知トリガー等）は、試行の判定後に「検証済みパターン」として追加する。現時点では確定仕様のみを v1.0 とする。

## 2.6 資源消費の制御（RSC）

| ID | 制御 |
|---|---|
| RSC-01 | 同一処理の再試行は 3回 までとする。上限を超えた場合は停止し、失敗として報告する |
| RSC-02 | 同一の操作で同一の結果が 2回 連続した場合は、進展なしとみなして停止し、報告する |
| RSC-03 | サブエージェントの並行実行は 3件 までとする。上限を超える委譲は直列化する |
| RSC-04 | 定期ジョブは1回の実行で終了する設計とする。異常な連続実行を検知した場合は止めて報告する |
| RSC-05 | 異常に長い入力は、文字数では一律に切らない。そのままでは他の文脈を圧迫する場合は、ファイル化または分割・要約してから処理する |
| RSC-06 | 重い処理は、起動前に同一処理の実行中・完了済みでないかを確認する |
| RSC-07 | 利用枠の急増を検知したら、新規の仕組みは足さず、そのまま報告する |

補足は次のとおりである。

- 進展が確認できる長時間処理は、上限の対象外とする。進展の有無は、処理量、出力、ログで判定する
- 停止した処理を自動で再開しない。再開は本人の判断による
- 消費量で課金・上限のある外部資源を使う作業は、開始前に上限（消費量ベース、金額換算つき）、計量方法、停止条件を決める。上限に達したら止めて報告し、有料枠へ自動で切り替えない
